# AGR Tools: общие правила реализации веток и кнопок

Обобщённые инструкции, по которым делалась волна 1.0 (#1024, ветки F…U). Они действуют для любой новой ветки AGR Tools (`adapters/max/agr_tools/`). Правила контрактов (паспорт, роли, окна, агент) — `docs/agents/agr-tools-1.0-rules.md`; точка входа — `docs/agr-tools/OVERVIEW.md`. Здесь только то, как работать с репозиторием, раннером и полигоном. Пути к машинам и папкам лаборатории не приводятся: их даёт карточка задачи.

## Основа и карточка

- Ветка стартует от актуального `origin/main`. Основу волны давала ветка 0: стадии и реестр `EDITS_100`, заглушки с фиксированными кросс-ветковыми сигнатурами, `contract_core` (роли, метки проёмов), хук журнала, схемы паспорта и агента, кнопки этапов в UI, подключение MCP, база полигона 1.0, правила в `AGENTS.md`, `library/README.md`.
- Работа идёт по карточке: кнопки и станции полигона, файлы, которые ветка может менять, файлы только для чтения, зависимости (лаборатория, порядок слияния), модель. Одна задача = одна ветка = один worktree = один пишущий агент (`AGENTS.md`).
- Лабораторные отчёты лежат в `docs/experiments/<id>.md`. Для строк старого плана читайте и их.
- Модель: геометрию, архитектуру и контракты ведёт основная модель; механику (лабораторные отчёты, обновление `expected`, CHANGELOG и документы, слияния) отдают Sonnet.

## Какие файлы можно менять

- Только файлы из карточки.
- Общие файлы не трогать: `runtime.py`, `ui_*.py`, `agr_tools.mcr`, `menu.ms`, `roadmap.py`, `agr_icons.py`, `tools/max/build_agr_tools.py`, `src/agr_mcp/tools.py`, README, `AGENTS.md`, `library/README.md`, `docs/plans/agr-tools-suite.*`, GUIDE, `polygon_core.py`, `bases.json`, `catalog.json`, `run_polygon.py`, README полигона.
- Модули чужой ветки или «ничьи» — только чтение.
- Если нужна правка в запрещённом файле — отдельный крошечный PR первым и запись в #1024. Кросс-ветковые вызовы — только по сигнатурам, зафиксированным в заглушках ветки 0; сигнатуру меняет владелец крошечным PR.
- CHANGELOG — только свой подраздел под «1.0.0 (#1024)».

## Как строить кнопку

1. Прочитайте раздел кнопки и контракт в #1024 и отчёт лота. Кнопка без лота начинается сразу; кнопка с лотом: сначала ядро и юнит-тесты, нативный прогон и слияние ждут лабораторного отчёта.
2. Логика — в `*_core.py` (stdlib, тесты без Max; headless Blender допустим для тяжёлых геометрических проверок). `*_max.py` — тонкий адаптер pymxs.
3. Каждый названный дефект → регрессионный тест: RED на поведении источника (модель источника) → GREEN на вашей реализации. Вердикт лаборатории важнее вердикта плана. Что в источнике не работает — исправляется.
4. Режим кнопки задаёт путь правки: `read` — только предпросмотр; `copy` — экспортная копия через `edit_core` / `edit_max`; `undo` — единая обёртка Undo ветки 0, выделение восстанавливается; `file` — только новая папка; `agent` — запрос плюс шлюз (контракт К4).
5. Всегда preview → apply с хешем, без перезаписи. Отчёт перечисляет сделано / пропущено / неоднозначно; пустой вход — ошибка. Метры через `units.SystemScale` (не `units.decodeValue`). Без новых глобалов MAXScript, без `clearUndoBuffer`, без схлопывания стека на оригиналах. Роли и метки — только по `contract_core`. Журнал пишет хук runtime, свой журнал не писать.

## Источники

- Ссылки на сторонний скрипт GeoAGR — только как цитата `GeoAGR.ms:<строка>`; код, фрагменты MAXScript и копии его таблиц в репозиторий не переносятся.
- Скрипты команды — читать, не копировать; указывать имя файла и SHA256 (#853).
- Код самого пилота переносить можно; оригиналы остаются на месте.
- Библиотеки с Google Диска (`library/README.md`) читать только с копии в своей scratch-папке.
- Область — только AGR Tools. Сторонние плагины (Forest Pack, RailClone, MultiScatter, RayFire, tyFlow, Chaos/Corona Scatter) не исследовать и их пакетное поведение не изучать; распознавать и предупреждать только по имени класса (`docs/plans/agr-tools-1.x.md` §2.3).
- Вопросы владельца в #1024 не блокируют: реализуйте названное умолчание параметром. Ответы владельца приоритетнее плана — `docs/decisions.md`.

## Тесты

Только в окружении `uv sync` вашего worktree: `uv run python -m pytest ...`. Перед слиянием — полный набор зелёный: минимум `tests/max_tools`, `tests/agr_mcp`, `tests/qa`, 0 failed; числа — в PR. Полный набор пилота большой, запускайте параллельно (`-n 4` и больше, см. `docs/agents/agents-reference.md`). Тесты на `AGENTS.md`, индексы, журнал решений и бюджет входа входят в набор — они ловят лишние строки в `AGENTS.md` и непривязанные решения.

## Полигон

- Свой фрагмент: `test-polygon/stations/<буква>.json`, `<буква>_build.py`, свой `expected/<id>.json` — минимум одна станция PASS и одна FAIL на кнопку.
- В PR показываются строки вашей кнопки из живого прогона полигона в Max 2024. Полный полигон один раз за ночь для всех запускает ветка релиза, не каждая ветка.
- Регенерация каталога: `test-polygon/polygon_core.py --catalog`, прогон: `python test-polygon/run_polygon.py` (см. `test-polygon/README.md`).

## AGR Lab runner (нативные прогоны Max/Blender)

- Нативный скрипт: `tests/max_tools/run_agr_tools_<slug>_native.py`, запускается раннером как `script_in_place` в batch Max 2024 на **одноразовых синтетических сценах**. `AGR_TEST_OUTPUT` — всегда новая папка, `AGR_TEST_PACKAGE` — собранный MZP.
- Постановка джоба: `python -m agr_lab submit <job.json> --wait 900` в репозитории `artsafro/agr-lab` на лабораторной машине; примеры джобов — в нём же. Где репозиторий и слоты, см. `docs/agents/CAPABILITIES.md` («Lab CI»).
- Корпусные здания — только копии и только если это сказано в карточке. Сцены владельца и GUI Max не трогать; не запускать Max самостоятельно; не трогать диспетчер, конфиг лаборатории и Hermes.
- Не больше 25 джобов раннера на ветку. Тринадцать веток делят два слота Max 2024, поэтому все кнопки ветки и строки полигона объединяются в один джоб. Раннер ставит в очередь: ждать, чужие джобы не отменять.
- Судить прогон по `run.txt` (выход 1 с «restore deferred» — зачтённый джоб). Статическое присутствие кода — не доказательство работы: нужен прогон.

## Git и PR

- Обычный `git push -u origin <ветка>`. Если сервер отклоняет push правилами репозитория (`commit_refs_rules`), публикация идёт запасным путём оркестратора через Git Data API; обходить отказ сменой аутентификации нельзя.
- Никаких force-push, `reset --hard`, rebase. Обновление ветки — `git merge origin/main` и повторный прогон тестов.
- PR в `main`, «Part of #1024»; для каждой кнопки: исправленные дефекты (имена тестов), результат приёмки, id джобов, строки полигона.
- Слияние — merge commit (не rebase, не squash), когда юнит-тесты и нативный прогон зелёные, после финального `git merge origin/main` и повторного прогона; кто именно сливает (ветка или оркестратор), сказано в карточке. После слияния — комментарий в #1024 и удаление удалённой ветки.
- `VERSION 1.0.0` и план `docs/plans/agr-tools-suite.json` меняют ветка 0 и ветка релиза, не вы.
- Зависимости слияния — в карточке (например, K после J; P после M, если M меняет `uvlayout`; Q после J, M, P).
- Агентам-исполнителям не писать оркестратору через `send_message`; итог — в своём чате: статус, тесты RED→GREEN по кнопке, id джобов, PR / SHA слияния, отклонения от карточки, открытые вопросы.

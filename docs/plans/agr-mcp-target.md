## Сводка в 10 строк

1. Цель проекта — сдаточные модели НПМ/ВПМ для ОКС, Ground, МАФ и Flora; AGR Tools 1.0 — конвейер этапов 0–9 с паспортом, ролями, библиотеками и шлюзом D108. Blender — второй полноправный хост.
2. `agr_mcp` даёт 52 инструмента: 8 фазы 0, 12 проверок 0.7, 13 правок 0.8 (одна из них правит сцену на месте), 19 предпросмотров 0.9. Нет ресурсов, прогресса, операций моделирования и разметки.
3. Замки, аудит, закреплённый процесс Max и закрытый `exec_unsafe` сделаны хорошо и покрыты тестами (40 тест-функций).
4. Вероятно, в Max с установленным 0.9.0 работают только 19 инструментов: каждая группа требует точную версию runtime, а в процессе Max допускается один модуль `runtime`. Живым запуском это не проверено.
5. Правило выделения из плана не реализовано: пустой `handles` берёт выделение пользователя или всю геометрию, проверки 0.7 выделяют узлы с находками.
6. Для apply агент должен вернуть весь отчёт preview, хотя план предполагал хранение на сервере. При таймауте замок снимается, пока Max ещё может работать.
7. Агенты этим MCP не пользуются: его нет ни в `.agents/mcp_config.json`, ни в `CAPABILITIES.md`, а лот L12 проверяет сторонний 3dsmax-mcp.
8. Ядро D108 (`dt_ai.ops`) уже есть на numpy, но в MCP не выведено. В Blender уже 179 файлов с bpy, из них 123 — разовые скрипты по объектам.
9. Все 22 `*_core.py` не импортируют pymxs, но 12 из них завязаны на handle и каналы Max. Жёстко привязаны к Max `runtime.py`, 19 `*_max.py` и Qt-панель.
10. Нет ни одной оценки «агент вместе с MCP решает задачу», хотя основа для неё есть: `twinqa/evals`, полигон с 92 ожидаемыми результатами, `agentlog`.

## Три главные рекомендации

1. **До ветки 0 или в ней:** снять точный пин версии runtime (проверять наличие функций и минимальную версию), ввести правило выделения, хранить preview на сервере (`preview_id`). Затем одним джобом agr-lab прогнать все инструменты против Max с 0.9.0 и зарегистрировать `agr-mcp` для агентов.
2. **Сделать MCP независимым от хоста и стабильным:** каталог генерируется из `agr-tools-suite.json` (около 30 инструментов по этапам вместо 52+), формат ответа v2 со сводкой и следующими шагами, общий журнал для панели и MCP. Каждая запись идёт транзакцией через шлюз D108 с откатом. Под это нужны интерфейс `HostAdapter` с `ObjRef` вместо handle и контракт передачи Max↔Blender: рабочий FBX с квадами, manifest и sidecar, автоматическая сверка круга.
3. **Мерить работу агента, а не только инструментов:** сценарные оценки на станциях полигона и на приёмке К4, позже оценка на эталонных триадах, всё в ночном Lab CI. Лот L12 должен проверять путь через `agr_mcp`. Паритет Blender начинать только после пяти критериев чекпоинта MVP (§4.5).

## 1. Глобальная цель и реальные задачи

### 1.1 Цель

- Продукт — сдаточные модели НПМ/ВПМ по московскому регламенту (позже IFC) для ОКС, Ground, МАФ (GroundEl), Flora и UCX, плюс Unreal (`README.md:3-4`, `AGENTS.md:12-15`). Приоритеты по порядку: архитектурная точность → масштаб и трансформы → материалы → производительность → визуал (`AGENTS.md:14-15`).
- AGR Tools 1.0 — «панель производства цифрового двойника ОКС, устроенная как конвейер Лего» (#1024). Состав (#1024):
  - этапы 0–9: паспорт → бадик → окна → капсулы → крыша → материалы → ВПМ → НПМ → НПМ↔ВПМ → сдача;
  - этап «Агент» с кнопками `agent.request` и `agent.accept`.
- Контракты #1024:
  - К1 — паспорт `jobs/<ID>/passport.json`, роли `agr_role`, журнал (#1024);
  - К2 — окна как стандарт с карантином (`:162-202`);
  - К3 — таблица материалов, библиотечный ID → плотные UDIM (`:204-234`);
  - К4 — агентский мост и шлюз D108 (`:236-261`);
  - К6 — UV шов к шову (`:271-278`).
- AGR Tools заменяет сторонний GeoAGR (`docs/plans/agr-tools-suite.md:6-9`). Одно ядро обслуживает две «морды»: Qt-панель и `agr-mcp` (`agr-tools-suite.md:20-23`, `:336-339`).
- Дополнение владельца (06.11, передано координатором): Blender — полноценный второй хост. После MVP в Max те же AGR Tools и тот же MCP строятся для Blender, а чистая квадовая модель возвращается Артёму в Max.

### 1.3 Где агенты помогают и где им нельзя

**Помогают** — работа на чтение и разметку, где нужно суждение и большой объём:
- классифицировать источник и предложить разбивку на части с картинками; пользователь подтверждает (`grill:118-121`);
- читать альбом: отметки, оси, легенда → таблица материалов и классы частей (`grill:145-150`);
- проём → тип окна по размерам и альбому (#1024);
- прогонять проверки и объяснять findings;
- готовить пакет и вопросы архитектору (D112, `grill:154-156`);
- вести конвейер preview → apply по кнопкам с подтверждением человека;
- после переноса в Blender — механическая геометрия (см. §3.12).

**Нельзя** (жёсткие правила):
- свободная правка меша поставки — только операции меню с инвариантами, откат и вопрос [D108] (`grill:80-82`, `docs/decisions.md:134`);
- решать конфликт «альбом против 3D» (`grill:154`);
- изобретать тип окна (`grill:212-213`), генерировать новые плитки (#1024);
- перезаписывать исходники и утверждённые версии (`AGENTS.md:61-62`);
- ставить `passed=true` при открытом гейте (`AGENTS.md:65`);
- трогать GUI-сеанс Max Артёма (план лабораторий #1024);
- исследовать сторонние плагины (`docs/agents/agr-tools-impl-rules.md`).

## 2. Инвентарь текущего MCP и поверхности агента

### 2.1 Сервер

- stdio, `mcp.server.lowlevel.Server`, один процесс на клиента. Реализованы только `list_tools` и `call_tool` (`src/agr_mcp/server.py:47-56`): нет resources, prompts, progress и отмены **[стат.]**.
- SDK `mcp==1.30.0`, протокол 2025-11-25, целевая ревизия 2026-07-28 не реализована (`src/agr_mcp/README.md:7-9`, `pyproject.toml:22,38`).
- Конверт ответа: `{tool_schema_version:1, server_version, result}`, валидируется по outputSchema (`server.py:93-94`). `result` — сырой отчёт runtime без сводки и пагинации **[стат.]**.
- Входы валидируются jsonschema до вызова, плюс отказ на NaN/inf. Каждый вызов, включая отказы, даёт одну строку аудита (`server.py:56-103`) **[тест]** (`tests/agr_mcp/test_agr_mcp.py:263,813`).

### 2.4 Разрывы и дефекты

Все пункты **[стат.]**, если не помечено иначе.

1. **Пин версии на группу ломает смешанный каталог [гип., высокий риск].**
   - Каждая группа требует точную версию runtime: 0.5.0, 0.7.0, 0.8.0 или 0.9.0 (`max_bridge.py:20-51,118-119`).
   - В одном Max допускается один модуль `runtime` (`max_bridge.py:77-80`).
   - Значит, в Max с установленным 0.9.0 (`runtime.py:8`) рабочими будут только 19 инструментов 0.9. Остальные 28 Max-инструментов дадут `version != expected` или «another module named runtime».
   - Нативный тест есть только для 3 инструментов на MZP 0.5.0 (`tests/agr_mcp/run_agr_mcp_native.py:5,96`). Следов живого вызова групп 0.7/0.8/0.9 через MCP я не нашёл.
2. **Контракт выделения из плана не реализован.**
   - План: пустой `handles` → ошибка `handles_required`, `select_findings=false`, сверка выделения до и после (`docs/plans/agr-mcp.md:108-134`).
   - Код: пустой `handles` берёт выделение пользователя или всю геометрию (`runtime.py:442-445`, `max_bridge.py:101-103`). Тест даже утверждает `handles=[]` как норму (`test_agr_mcp.py:188`).
   - `checks_070` выделяет узлы с findings (`runtime.py:304`).
3. **Нет выбора экземпляра.**
   - Только env-пин, нет параметра `instance` и списка экземпляров.
   - В аудите нет `max_pid` и `max_version` (план `agr-mcp.md:200-214,225` против `audit.py:15-16`).
4. **Apply гоняет preview через LLM.**
   - Агент обязан вернуть «неизменённый» полный отчёт preview (`tools.py:259-264`).
   - Это токены, риск искажения моделью и отказ `StalePreview`.
   - План предполагал, что preview хранит сервер (`agr-mcp.md:160`).
5. **Lease при таймауте.** При таймауте трубы сервер сообщает «Max may still be running; do not resend» (`max_pipe.py:72-73`), но `finally` всё равно снимает замок (`locks.py:383-386`). Следующий вызов попадёт в занятый Max **[гип.]**.
6. **Домен замков.**
   - Один глобальный файл `agr-3dsmax-live.lock` на все экземпляры Max (`locks.py:39`).
   - Он не связан со слотами agr-lab (README agr-lab).
   - Действия человека в панели того же Max им не покрыты.
7. **Ни одной операции моделирования и разметки.** Ядро D108 уже есть в `src/dt_ai/ops`:
   - `run_operation` с откатом (`src/dt_ai/ops/operations.py:44-61`);
   - операции `keep`, `embed_into_neighbour`, `primitive_box`, `to_opacity_plane` (`:63-157`);
   - инварианты видимости D115 (`src/dt_ai/ops/invariants.py:1-20,359`).

   В MCP ядро не выведено. Операций К4 (`set_role`, `mark_opening`…, #1024) нет; нет `ops_d108.py`, `AgentRequest.schema.json` и `journal_core` (сверено по листингам `src/agr_mcp`, `schemas/`, `adapters/max/agr_tools`).
8. **Агенты им не пользуются.**
   - В `.agents/mcp_config.json` зарегистрирован `3dsmax-mcp`, а `agr-mcp` — нет.
   - В `docs/agents/CAPABILITIES.md` раздела `agr-mcp` нет, поэтому по `AGENTS.md:73` это ещё не общий инструмент.
   - Гейт навыков `.claude/settings.json:119` матчит только `3dsmax|blender|revit`.
   - Лот L12 проверяет живой Max через **3dsmax-mcp** (план лабораторий #1024), а не через `agr_mcp`.
9. **Формат для LLM.**
   - 52 инструмента в плоском списке; описания шаблонные («An empty stub answers status not_implemented», `tools.py:364-366`).
   - Нет сводки, следующих шагов и ссылок на правила.
   - Большой отчёт `census` уходит целиком.
10. **Blender.**
    - Только headless readback и `validate_package scene=true` (`tools.py:313-326`).
    - Живого Blender и операций нет.
    - Замок `agr-blender-batch.lock` отделён от слотов Blender в agr-lab.

### 2.5 Тесты: что они доказывают

## 3. Целевой дизайн MCP для домена

### 3.1 Принципы

1. **MCP — типизированный фасад того же ядра, что у панели.** Одна функция ядра — два фронта (`agr-tools-suite.md:20-23`). Логика в `*_core.py` (разбиение #1024), не в MCP.
2. **Нейтральность к хосту.** Один контракт инструмента и одно ядро; тонкие адаптеры Max (`*_max.py`, pymxs) и Blender (`*_bpy.py`, bpy/bmesh); офлайн-ядро на numpy.
3. **Агент не получает кода.** Только операции с enum-параметрами, путями, id и preview_id. `exec_unsafe` доступен только в профиле `dev`.
4. **Любая запись — транзакция под шлюзом D108.** Схема: preview → apply по preview_id → инварианты до и после → откат и вопрос.
5. **Контекст — ресурсами, а не вставкой в промпт** (карточка U (#1024)).

### 3.2 Таксономия инструментов

Около 30 инструментов в профиле, сгруппированных по этапам. Строки плана — это значения `op` и `check_id`, а не 52+33 отдельных инструментов. Имена `agr_<block>_<name>` остаются id операций.

| Класс | Инструменты | Заметки |
|---|---|---|
| Контекст (read) | `agr_project_get`, `agr_stage_status`, `agr_scene_snapshot(scope, page)`, `agr_object_get(ids)`, `agr_library_query(kind=windows\|materials\|maf, filter)`, `agr_journal_tail(n)`, `agr_instances_list` | snapshot: роли, слои, метки `OPEN_*`, `LEVEL_*`, счётчики; страницы по 200 объектов |
| Проверки | `agr_check_run(check_ids[], target)`, `agr_stage_gate(stage)`, `agr_package_validate`, `agr_fbx_readback` | `check_ids` — enum из `agr-tools-suite.json` (`mcp: yes`) |
| Разметка (агентский слой) | `agr_mark_role`, `agr_mark_opening`, `agr_set_library_id`, `agr_place_window`, `agr_make_capsule`, `agr_make_roof_plane` | операции К4 (#1024); пишут только в `AGENT_<req>` |
| Операции (preview/apply) | `agr_op_preview(op, target, params)` → `preview_id`; `agr_op_apply(preview_id)`; `agr_op_rollback(txn_id)` | `op` — строки 1.0 и меню D108 (`keep`, `primitive_box`, `rebuild_by_contour`, `embed_into_neighbour`, `to_opacity_plane`) |
| Хендофф Max↔Blender | `agr_handoff_export(target, profile)`, `agr_handoff_import(bundle, mode=agent_layer)`, `agr_handoff_verify(bundle_a, bundle_b)` | §3.12 |
| Джобы | `agr_job_submit(kind, inputs)`, `agr_job_status`, `agr_job_result`, `agr_job_cancel` | batch Max и Blender через agr-lab |
| Визуал | `agr_render_views(target, views, mode=shaded\|face_orientation\|matid\|album_overlay)` | картинки плюс числа (§3.10) |
| Эскалация | `agr_question_add`, `agr_request_create`, `agr_request_accept` | вопросы в паспорт и `questions.md` |
| Отладка | `agr_exec_unsafe` | только профиль `dev` |

Правило гранулярности: инструмент = осмысленное действие этапа (уровень кнопки), а не примитив сцены (`move vertex`). Тяжёлые цепочки — одним `op` с `steps` в отчёте.

### 3.3 Контракт мутации (шлюз D108)

1. `preview` вычисляет план и `state_hash` (как `edit_core.require_current`, `edit_core.py:5-8`).
2. Сервер хранит preview: `preview_id = sha256(canonical(report))`, TTL. Preview привязан к хосту и экземпляру, документу, версии ядра и `state_hash`.
3. Агенту возвращается краткий diff: что будет создано, изменено и удалено, по ролям и объектам.
4. `apply(preview_id, idempotency_key)`:
   - lease хоста;
   - свежий fingerprint (сверка с preview);
   - хеши объектов вне целевого слоя;
   - одна запись Undo (Max) или undo-push/snapshot (Blender);
   - выполнение;
   - инварианты этапа и D115-видимости (для меша — через `dt_ai.ops.invariants`);
   - сверка хешей вне слоя.
5. При нарушении: undo, затем повторная сверка хешей (доказательство отката), затем `status: rolled_back` + `question`.
6. Подтверждение человека для классов `undo-in-place` и `destructive`: в доке — кнопка «Применить» (карточка U (#1024)); в CLI — MCP elicitation или токен подтверждения, выданный UI. Без подтверждения apply отвечает `needs_human`.
7. Классы и аннотации инструментов: `read` < `select` < `markup(agent layer)` < `copy`/`file` (новые пути, без перезаписи) < `undo-in-place` < `destructive`.

### 3.4 Маршрутизация по хостам

| Хост | Когда | Канал |
|---|---|---|
| `offline` | ядро на JSON, FBX, PNG, GeoJSON | процесс сервера |
| `blender-batch` | readback, инварианты, геометрическое ядро D110 (`grill:106-111`), рендер-листы | слот Blender agr-lab, `--factory-startup` |
| `max-batch` | всё, что воспроизводимо на копии `.max`: полигон, проверки, `copy`/`file` | слот Max agr-lab (ini/профиль изолированы, README agr-lab) |
| `max-live (agent slot)` | UI-тесты, undo, док (L12) | отдельный экземпляр в изолированном слоте |
| `max-live (owner)` | только док Артёма, с подтверждением | свой listener в процессе Max, очередь на главном потоке (карточка U (#1024)) |
| `blender-live` | после паритета, для интерактивной доводки | свой аддон-мост, не сторонний |

Как выбирается хост:
- поле `host` выбирается автоматически по классу операции, но его можно задать явно;
- `instance` обязателен, когда живых экземпляров больше одного (правила `agr-mcp.md:204-212`).

Выход из зависимости от 3dsmax-mcp: свой минимальный listener в Max. Сторонний TCP-слушатель 8765 и так в списке рисков.

### 3.5 Длительные операции

- Всё, что дольше ~20 с, идёт джобом: `job_id`, прогресс (MCP progress/tasks, если SDK умеет, иначе опрос `agr_job_status`), отмена убивает только своё дерево процессов (README agr-lab).
- Lease держится, пока хост не подтвердил idle. Таймаут клиента не снимает замок с занятого Max (исправляет п. 2.4.5).
- Результаты — файлы с SHA-256 в `runs/<job>`; агенту отдаются URI ресурсов.

### 3.6 Контекст и ресурсы

Шаблоны ресурсов:
- `agr://project/{id}/passport` и `/journal`;
- `agr://scene/{host}/{doc}/snapshot`;
- `agr://library/windows` (без карантина, #1024) и `agr://library/materials`;
- `agr://rules/{area}` (`docs/domain`);
- `agr://decisions/{D}`;
- `agr://report/{id}` — полный отчёт по ссылке.

Prompts: по одному на этап («Этап 2: окна»). Это сценарий, а не правило: правила остаются в репозитории.

Защита от инъекций: имена объектов, user props и тексты альбома — данные. В ответах они идут в отдельных полях и экранируются.

### 3.7 Формат результата для LLM

`content` (текст) — сводка до 10 строк. `structuredContent`:

```json
{"tool_schema_version":2,"status":"pass|fail|rolled_back|needs_human|not_implemented",
 "summary":"…","counts":{"objects":120,"findings":7},
 "findings_top":[{"code":"udim_id","object":"SM_X_Main","handle":42,"rule":"V008","why":"…","suggested_op":"agr_udim_slots"}],
 "truncated":true,"report_uri":"agr://report/…","preview_id":"…","txn_id":"…",
 "artifacts":[{"uri":"…","sha256":"…"}],"next_actions":["agr_op_apply(preview_id)","agr_question_add(…)"]}
```

Ошибки — машинные коды: `busy`, `stale_preview`, `scene_mismatch`, `version_mismatch`, `instance_ambiguous`, `invariant_broken`, `needs_human`, `host_unavailable`.

### 3.8 Профили и права

Профиль выбирается через `AGR_MCP_PROFILE`; `tools/list` показывает только инструменты профиля.

| Профиль | Что доступно | Кто |
|---|---|---|
| `observer` | контекст и проверки | ревью, Antigravity |
| `operator` | плюс разметка в агентском слое, `copy`/`file`, джобы | рой, док по умолчанию |

### 3.9 Аудит, журнал, конкуренция

- **Один журнал.** Аудит MCP и журнал панели К1 (#1024) сливаются в одну схему строки:
  - `ts`, `actor (panel|mcp|agent)`, `tool/op`, `host`, `instance`, `doc`;
  - `state_hash_before/after`, `preview_id`, `txn_id`, `status`, `counts`, `duration`;
  - `card`, `client`, версии ядра и адаптера.

  Журнал копируется в `jobs/<ID>/journal.jsonl`.
- **Конкуренция.**
  - Lease на экземпляр (pid + токен fencing), а не один файл на «весь Max». Read-only вызовы можно разделять, пишущие — эксклюзивно.
  - Панель тоже берёт lease перед apply, чтобы человек и агент не писали одновременно.
  - Batch идёт только через очередь agr-lab: 13 веток на 2 слота (разбиение #1024).
  - Когда к одному Max подключаются док, CLI и рой, нужен один демон на хост (локальный Streamable HTTP) вместо stdio-процесса на клиента. Это предусмотрено планом как будущее (`agr-mcp.md:190`).

### 3.10 Визуальная проверка

### 3.11 Оценка: решает ли агент с MCP задачу

1. **Контракт.** Существующие тесты плюс равенство «MCP == ядро» для **каждого** инструмента на фейковых pymxs и bpy.
2. **Нативное равенство на полигоне.** Станции `test-polygon/expected/*.json` (92 файла) через MCP в слоте agr-lab: каждая кнопка даёт тот же код.
3. **Сценарные evals агента** (новые задачи в `evals/`):
   - «сделай станцию 1.0.N зелёной»;
   - приёмка К4: имитация агента ставит метки и проходит шлюз; задетый объект вне слоя → откат (#1024);
   - «разметь проёмы KPP1 → типы окон», с графером против эталона.
4. **Capability на триадах эталона** (D114, `grill:165-173`; `twinqa/evals/capability.py`): силуэт, бюджет, согласие по решениям, SINTEZ — против людской поставки.
5. **Безопасность:**
   - инъекция в имени объекта;
   - попытка apply без preview, попытка писать вне слоя;
   - два агента на один экземпляр.
6. **Метрики** через `agentlog`: вызовов на задачу, доля ошибок, повторы, время, токены.

Ночной прогон — в Lab CI (README agr-lab).

- `sidecar.json` — то, что FBX теряет или искажает: user props (`agr_role`, `agr_window_type`, `agr_opening`, `LEVEL_*`, метки `OPEN_*` как хелперы), сглаживание и hard edges, ссылки на паспорт.

Что обязано пережить круг (проверка `agr_handoff_verify` = readback обеих сторон плюс сравнение):

| Свойство | Допуск | Риск |
|---|---|---|
| Имена объектов и роли | 1:1 | Blender укорачивает имена и добавляет `.001` [гип.] |
| matID ↔ слоты | 1:1 по таблице | в Blender нет matID, только индекс слота; Multi/Sub разворачивается в слоты [гип.] |
| UV/UDIM | целые части тайлов равны; дробная часть ≤ 1e-6; метрика шва = 0 (К6) | порядок UV-каналов |
| Нормали и сглаживание | hard edges и custom normals равны; Face Orientation без новых красных пикселей | smoothing groups ↔ sharp edges |
| Единицы, ось, масштаб | метры, scale 1, bbox ±0.1 мм | `unit_scale`/`apply_unit_scale`, Y-up/Z-up |
| Пивоты и трансформы | world matrix ±1e-5 | `bake_space_transform` |
| Топология | квады и n-гоны сохранены, число полигонов и рёбер равно | триангуляция при экспорте |
| Инстансы | сохранены как инстансы | FBX-экспорт может «распаковать» инстансы |

Дефолт для Артёма: Blender возвращает модель в слой `AGENT_<req>` его сцены через `agr_handoff_import`, а перенос делает шлюз `agent.accept`. Свободной записи в его объекты нет.

## 6. Мнение оркестратора (06.11.2026)

*Мнение оркестратора на момент релиза 0.9.0, до работ ветки 0 и U: пункты о пине версий и разбиении на инструменты к 1.0.0 уже исполнены (таблица в начале файла).*

Я прочитал отчёт и сверил с кодом два ключевых утверждения:

- **Пин версии (§2.4.1) подтверждаю [стат.].** В `src/agr_mcp/max_side/max_bridge.py:87-89` версия сверяется на точное равенство, а строки `:118-119` выбирают ожидаемую версию по группе. Строки `:77-80` запрещают второй модуль `runtime`. Поэтому при установленном 0.9.0 вызовы групп 0.5, 0.7 и 0.8 будут отказывать. Живым запуском это не проверено, но по коду иначе быть не может.

**В целом с отчётом согласен.** Он сходится с моей независимой позицией: инструменты — это глаголы конвейера, preview→apply, шлюз D108 в сервере, профили прав, джобы для долгих операций, ресурсы для неизменных знаний. Сильнее моего в нём: конкретные дефекты текущего кода (пин версий, выделение, снятие замка при таймауте), то, что агенты MCP вообще не используют, и полный раздел про Blender с контрактом хендоффа.

**Где расставил бы акценты иначе:**

1. **Пин версий — до релиза R или сразу после, отдельным маленьким PR.** Это не блокер панели 0.9.0, но MCP, выпущенный в 0.9.0, на практике отдаёт только 19 из 52 инструментов. В примечаниях к релизу это надо записать честно либо исправить до выпуска. Я бы исправил сразу после релиза, чтобы не задерживать R.
2. **Сокращение до ~30 инструментов — да, но без потери прямых имён на первом шаге.** Агенты лучше выбирают конкретный инструмент с понятным описанием, чем `agr_op_preview(op=…)` с enum из 50 значений. Компромисс: генерировать каталог из `agr-tools-suite.json`, сохранить отдельные инструменты для больших кнопок этапов (около 15), а мелкие строки свести в `agr_check_run`/`agr_op_*`. Лучший вариант покажет сценарный eval.
3. **Один демон на хост (§3.9) поставил бы раньше, в ветку U, а не «в будущем».** Док, CLI и рой на одном Max через stdio-процессы с файловым замком — источник гонок. Это то же решение, что и свой listener вместо 3dsmax-mcp, так что его лучше сделать одним шагом.
4. **Blender: начать хендофф раньше чекпоинта, но маленьким.** Полный паритет — после MVP, согласен. Но контракт хендоффа (manifest + sidecar + `agr_handoff_verify` на синтетике, критерий 5) почти не зависит от Max-веток и снимает главный риск паритета — потери в FBX-круге. Его можно поручить одному Sonnet-агенту параллельно с волной 1.0, не трогая её файлы.
5. **Оценка агента — главный пробел.** Без сценарных eval нельзя доказать, что MCP помогает, а не только «работает». Минимум к R 1.0: три задачи из §3.11 п. 3 в ночном Lab CI.

**Что предлагаю сделать:**
- в ветку 0: генерация каталога, конверт v2 с `preview_id`, общий журнал, исправление пина и выделения;
- в ветку U: демон на хост со своим listener, шлюз D108 через `dt_ai.ops`, профили;
- L12 переключить на проверку пути через `agr_mcp`;
- отдельной небольшой задачей вне волны: контракт хендоффа Max↔Blender на синтетике.

Вопросы §5 оставляю владельцу. Мои рекомендации по ним совпадают с рекомендациями отчёта.

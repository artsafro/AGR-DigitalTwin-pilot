# GeoJSON FNO_code: do non-string and Unicode-digit values bypass the official format check?

Report-only research, pilot repository. No production code, test, standard, hook, CI or data change. No pytest and no full suite were run (card rule).

## Summary

- **Yes, both bypass it.** In OKS single-file `validate_package.py --profile vpm --json`, `FNO_code` of `123`, `1234`, `true`, `[]`, `{}` (non-string) and the 3-character strings `١٢٣` (Arabic-Indic), `１２３` (fullwidth), `²²²` (superscript two) all give V011 = `pass` with a `schema` pass finding. Measured, 8 of 8.
- Cause (read and measured): the format branch runs only for `isinstance(value, str)` and uses `str.isdigit()`, which is true for all Unicode digit classes, including superscripts.
- `null` and `""` are caught as `FNO_code empty` (fail) in OKS; malformed ASCII `1234`, `abc` give `FNO_code format` (fail). The D011 rule (mandatory, 3/6/9 digits) holds for ASCII strings only.
- Ground (file stem `*_Ground`): `null` and `""` pass as the documented exemption (PKG-21). Also measured and not documented: Ground never gets a format check at all, so `1234` and `abc` pass V011 in Ground (PKG-21 exempts only emptiness).
- The caller keeps V011's verdict: the single-file report shows V011 `pass` and the same findings list; report `passed=false`, exit 2 anyway because 11 stages are `not_run`. There is no `delivery_passed` field in this report; `passed=false` is the only delivery signal, so a V011 pass here is a helper pass, not delivery acceptance.
- Two bounded follow-ups proposed (below); policy questions are for the user.

### Reading the result

- Clean ASCII control: reproducible baseline, V011 pass, exit 2, report `passed=false`.
- Malformed ASCII (`1234`, `abc`): measured `FNO_code format` fail in OKS. This is the only place the official format check fires.
- All 8 non-string/Unicode mutations pass V011 in OKS: the first non-empty check at line 129 compares by equality with `""`/`None` only (`0`, `False`, `[]`, `{}` are not equal), and line 131 skips non-strings. For the Unicode strings `isdigit()` is true for Arabic-Indic, fullwidth and superscript two (`'²'.isdigit()` is True, `'²'.isdecimal()` False), and the length is 3.
- Not measured (outside the matrix): other whitespace such as tabs or NBSP, 6/9-character Unicode strings, float values, whether the later Blender/FBX stages read `FNO_code`.
- D011 preserved: nothing here changes OKS-mandatory `FNO_code`; empty/`null` still fails in OKS. Ground exemptions preserved: `null`/`""` pass and are measured separately from OKS.
- Observed V011 pass is **not** delivery acceptance: all 32 reports have `passed=false`, and the type-bypass rows would have been wrong deliveries had other stages passed.

## Open questions for the user

1. Must `FNO_code` accept only ASCII digits `0-9` (reject Arabic-Indic, fullwidth, superscript), or is any Unicode decimal digit acceptable?
2. For a JSON number or bool (`123`, `true`) or `[]`/`{}`: fail, review, or coerce to a string? (Coercion would hide a customer-data error; the D011 text says never invent values.)
3. Should a wrong type and a wrong format be `fail` (as now for malformed ASCII) or `review`?
4. Ground: is a non-empty malformed `FNO_code` (`1234`, `abc`) allowed, or should only empty be exempt as written in PKG-21?
5. Should the single-file report get an explicit `delivery_passed` field, or is `passed=false` plus `not_run` stages enough?

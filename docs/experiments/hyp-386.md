# Hypothesis #386: shared local-object transforms keep UCX FBX gaps at 14 km within 0.01 mm

**Verdict: CONFIRMED.** Every mandatory check passed on the local arm (B), in both repetitions. The
worst imported gap error in all 54 local-arm pairs is **0.000052 mm**; the limit is 0.01 mm. That includes
37° at (-1170,-14200,0) m, the case #281 failed with baked vertices. The baked control (A) reproduced
**2.440089510 mm** exactly in both repetitions, so the comparison is valid. `delivery_passed=false`. The
geometry is synthetic stress geometry, not data from a real object.

## Claim (issue #386)
The unchanged #281 six-box population can be stored as untransformed local vertices, with every box given
the same object rotation/translation matrix. Through Blender 5.1.2 FBX export and a fresh import, all
3/4/6 mm gaps then stay within 0.01 mm of nominal, including the rotated 14.2 km case.

## Observations (recorded, not part of the verdict)
- In arm B the gap error does not depend on the translation. The residual of about 5e-5 mm is float32
  rounding of the local coordinates (for example 2.003 m), which is already present before FBX.
- The FBX roundtrip changes the matrix decomposition. Blender stores an Euler XYZ rotation, and the
  imported matrices pick up about 4e-8 X/Y tilt terms. The max element deviation from the set M is 2.2e-6,
  at 89°. All six imported matrices are still identical within each scene, so the gaps are unaffected (a
  rigid shared transform). Corner positions move by up to 0.021 mm at 89°, against 0.0003 mm before FBX.
  That is far below 0.5 mm but is still an FBX effect, not zero.
- Imported translations come back exact (e.g. -1170.0, -14200.0). The large coordinate lives only in the
  float32 matrix translation, which represents these integer-metre offsets exactly. A non-integer offset at
  14 km would be quantised to float32 spacing (about 1 mm at 14 km). That shifts all six boxes together,
  so gaps are unchanged, but absolute position is not; this experiment did not test it.
- The experiment makes no claim about which part of the FBX route causes this, and it does no binary FBX
  parsing.

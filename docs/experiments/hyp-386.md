# Hypothesis #386: shared local-object transforms keep UCX FBX gaps at 14 km within 0.01 mm

**Verdict: CONFIRMED.** Every mandatory check passed on the local arm (B), in both repetitions. The
worst imported gap error in all 54 local-arm pairs is **0.000052 mm**; the limit is 0.01 mm. That includes
37° at (-1170,-14200,0) m, the case #281 failed with baked vertices. The baked control (A) reproduced
**2.440089510 mm** exactly in both repetitions, so the comparison is valid. `delivery_passed=false`. The
geometry is synthetic stress geometry, not data from a real object.

## Claim (issue #386)
The unchanged #281 six-box population can be stored as untransformed local vertices, with every box given
the same object rotation/translation matrix. Through Blender 5.1.2 FBX export and a fresh import, all
3/4/6 mm gaps then stay within 0.01 mm of nominal, including the rotated 14.2 km case.

## Setup
- Base: pilot `main` @ `2fd3b2e428880419d844a10b0ffe1e2a2cc184b5`. Blender 5.1.2, headless
  (`--background --factory-startup --disable-autoexec --python-exit-code 1`). Python 3.14.7.
- Predictions were frozen in commit `5e132ca` before any native run (`experiments/hyp-386/predictions.json`,
  which also records the input sha256s). Nothing was retuned after the run.
- Arm A: the unchanged `tools/export/export_mesh_blender.py`, with R*p+T baked into the vertices.
- Arm B: `experiments/hyp-386/export_local.py`, a copy of the exporter with one change: if a dump mesh
  has `matrix_world`, the local vertices go to `from_pydata` and that matrix becomes `obj.matrix_world`. A
  4th argument writes a pre-FBX receipt: raw float32 `co`, the stored matrix as Python floats, and the
  binary64 world reconstruction. Names, topology, material slots, units, validation and FBX options are
  the same as production. It uses no parenting, `transform_apply` or per-box origin.
- Readback: `experiments/hyp-386/readback.py`, a copy of the #281 readback. Each FBX is imported in a
  fresh factory-startup process, and every matrix and `co` component is promoted to a Python float before
  the scalar sums. No `Matrix @ Vector`.
- Measurement: unchanged `twinqa.geometry.ucx_audit` (`weld`, `pair_relation`, `is_closed`, `is_convex`,
  `face_planes`). The oracle is Python `math.sin/cos` R*p+T on the analytic corners. Corner distance is
  the symmetric nearest-corner distance.
- Matrix: angles 0/37/89°, T ∈ {(0,0,0), (100,100,0), (-1170,-14200,0)} m, gaps 3/4/6 mm (three pairs
  per scene). That gives 9 scenes × 2 arms × 2 repetitions = 36 export + 36 import native calls, each in a
  fresh path. All returned rc=0.
- Command: `PYTHONPATH=src python experiments/hyp-386/driver.py %LOCALAPPDATA%/Temp/agr-blender-t_51071800/run experiments/hyp-386/results.json`
- Evidence: `experiments/hyp-386/results.json` (every row, gap, corner distance, stored and imported
  matrices, timings). `experiments/hyp-386/raw/` holds the 18 pre-FBX receipts and 36 readback dumps
  (raw vertices, matrices, binary64 world).

## Observations (recorded, not part of the verdict)
- In arm B the gap error does not depend on the translation. The residual of about 5e-5 mm is float32
  rounding of the local coordinates (for example 2.003 m), which is already present before FBX.
- The FBX roundtrip changes the matrix decomposition. Blender stores an Euler XYZ rotation, and the
  imported matrices pick up about 4e-8 X/Y tilt terms. The max element deviation from the set M is 2.2e-6,
  at 89°. All six imported matrices are still identical within each scene, so the gaps are unaffected (a
  rigid shared transform). Corner positions move by up to 0.021 mm at 89°, against 0.0003 mm before FBX.
  That is far below 0.5 mm but is still an FBX effect, not zero.
- Imported translations come back exact (e.g. -1170.0, -14200.0). The large coordinate lives only in the
  float32 matrix translation, which represents these integer-metre offsets exactly. A non-integer offset at
  14 km would be quantised to float32 spacing (about 1 mm at 14 km). That shifts all six boxes together,
  so gaps are unchanged, but absolute position is not; this experiment did not test it.
- The experiment makes no claim about which part of the FBX route causes this, and it does no binary FBX
  parsing.

- Out of scope: production `tools/export/export_mesh_blender.py`, `src/twinqa/geometry/ucx_audit.py`
  and UCX builders stay unchanged. No coordinate convention, delivery gate, tolerance or scene policy
  changes. Choosing a local-origin convention for production needs a separate user decision.

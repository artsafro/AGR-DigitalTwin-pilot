# Hypothesis #101: IFC relation multimaps retain competing links without overwrites

Verdict: **CONFIRMED** (synthetic, deliberately cardinality-invalid IFC only). `delivery_passed=false`.
Issue: https://github.com/artsafro/AGR-DigitalTwin-pilot/issues/101

All inputs are **synthetic** IFC4 files written by the tracked probe writer from benchmark specs. The 18 malformed
copies are deliberate fault injections, not Revit-export examples. Nothing here says anything about real exports,
about which host is correct, or about where a production adapter should live.

## Claim

A relation multimap with explicit cardinality diagnostics exposes competing IFC host (void), fill and containment
relationships that the current semantic-loss ledger (`experiments/bim-revit-agr/ifc_probe.py:read_ledger`)
collapses to one endpoint. It leaves every clean relationship unchanged and keeps all relation IDs and endpoints
as evidence.

  Generated IFCs and `injections.json` go to the scratch dir only. The committed raw evidence is

### Inputs and injections

- Specs (sha256): b01 `48d6fa46…e4a8`, b02 `85f1b7d2…0bea`, b02t `4a9a5aa7…2cec`

- The clean manifest comes from the driver's own raw enumeration (`_relation_records`), not from `census`.
- 3 malformed copies per clean file (18 in total). Each copy reopens the saved clean file and adds one relation
  with `ifc.create_entity` and a fresh `ifcopenshell.guid.new()`. The original relation stays. No `ifcopenshell.api`
  is used. Targets are chosen by the smallest GlobalId from the raw manifest:
  - void: the first opening gets a second `IfcRelVoidsElement` to a wall that is not its host;
  - fill: the first opening gets a second `IfcRelFillsElement` to a window that is not its fill;
  - contain: the first contained wall gets a second `IfcRelContainedInSpatialStructure` to a storey that is not its container.
- The injection manifest (`injections.json` and `malformed[].injection` in `results.json`) is written from the
  injection itself. After saving, each copy was reopened and checked: both relation GlobalIds and endpoints are
  present, the product GlobalId set is identical, and the raw record multiset equals the clean records plus exactly
  the injected record.
- GlobalIds come from `ifcopenshell.guid.new()`, so the IFC sha256 values change from run to run. The per-file
  hashes of this run are in `results.json` (for example b01-m clean `04238f1e44dc…`, b01-m-dup-void `9e26ae84a71a…`).

### Baseline overwrite path (raw evidence)

`read_ledger` builds `pairs()` as `out[a.GlobalId] = b.GlobalId` for voids and fills, and
`contained[el.GlobalId] = host` for containment (`ifc_probe.py` lines 186-198). The last relation in `by_type`
order wins. On all 18 copies the baseline selected the **injected** endpoint (the newer relation, written last).
The original host, fill or storey disappeared from the ledger without any `issues` line. Example (b01, m, void):
opening `2ywN_h2SP9URmOj8MA1lU3`, original wall `2H3jCrWsD9rBy3vhbkWdfz` (rel `0WO5UR9uT7YBJm7gL2B_jP`),
injected wall `03SacYEzL5$fm_1vSeYZRv` (rel `28Ljoju4DBxgcvzcutnap0`). Baseline `host_id` = `03SacYEzL5$fm_1vSeYZRv`.
Candidate: `{"family":"void","endpoint_ids":[both walls],"relation_ids":[both rels],"status":"unresolved","selected_endpoint":null}`.
The full 18 cases are in `results.json` → `malformed[]`.

## Verdict

**CONFIRMED.** Every condition was met: the baseline collapsed 18/18 (threshold ≥ 1); the candidate was correct on
18/18 with 0 false positives, 0 false negatives, 0 lost records or products and 0 saved-relation losses; the clean
controls had 0 diagnostics and exact endpoint and record parity (6/6); the evidence was stable on 24/24 files in
both iteration orders over 3 reads. `delivery_passed=false`.

Limits: one synthetic writer and three relation families. One injected conflict per file. A reverse conflict
(one window filling two openings) is not flagged, because multiple openings per filler is out of scope.
IFC2x3, real Revit exports and missing-fill policy were not tested. The production-adapter location and
real-export policy are user decisions and stay open.

## Adoption scope (if adopted, separate card)

- Add a report-only relation census helper beside `experiments/bim-revit-agr/ifc_probe.py` (the logic of
  `experiments/hyp-101/relation_multimap.py`). Integrate it into `read_ledger` so the ledger keeps raw relation
  evidence (`relation_id`, source, endpoint) and puts explicit `unresolved` conflicts in its output. Keep the
  existing singleton fields and the missing-link diagnostics unchanged for valid files.
- New test `experiments/bim-revit-agr/test_relation_cardinality.py` covering: a clean file has zero diagnostics and
  unchanged `host_id`/`fill_id`/`storey_id`; each of void, fill and contain duplicates gives exactly one diagnostic
  with both endpoint IDs and both relation IDs and no selected endpoint; forward and reverse order give identical
  output; raw records are not dropped.
- Do not choose a production adapter location, dependencies or real-export policy (user decisions).
